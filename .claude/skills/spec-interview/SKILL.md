코드를 쓰기 전에 무엇을 어떻게 만들지 사용자와 합의하고, 합의한 내용을 스펙 문서로 남긴다. 스펙을 사용자가 확인하기 전에는 구현을 시작하지 않는다.

## 1. 먼저 조사한다

질문하기 전에 코드베이스를 읽는다. 코드가 답해 주는 것은 묻지 않는다.

- 이 변경이 닿는 파일, 비슷한 기존 구현, 따라야 할 패턴
- 깨뜨리면 안 되는 것(테스트, 호출하는 쪽, 설정)
- 프로젝트 지침(`CLAUDE.md` 등)에 이미 적힌 결정

조사한 뒤에도 남는 것만 사용자에게 묻는다.

## 2. 한 번에 하나씩 묻는다

결정할 것을 의존 순서대로 늘어놓고 앞에서부터 하나씩 묻는다. 앞의 답이 뒤의 질문을 바꾸기 때문이다.

- 질문마다 **추천안과 이유**를 같이 제시한다. 사용자가 "추천대로"라고 답할 수 있게 한다.
- 보기를 줄 때는 서로 겹치지 않는 선택지만 준다.
- 사용자가 답하면 그 답이 앞의 결정과 부딪히지 않는지 확인하고, 부딪히면 바로 짚는다.
- 질문을 한꺼번에 쏟지 않는다.

특히 아래는 코드만 봐서는 알 수 없으니 반드시 확인한다.

- 이 변경의 목적과 하지 않을 것(범위 밖)
- 성능, 호환성, 일정 같은 제약
- 되돌리기 어려운 결정(데이터 형식, 외부에 공개되는 인터페이스)
- 이 작업이 끝났다고 판단할 기준

## 3. 스펙 문서를 쓴다

합의가 끝나면 아래 항목으로 문서를 만든다.

1. **목표**: 무엇을 왜 하는가
2. **하지 않을 것**: 이번 범위 밖
3. **결정 사항**: 결정과 그 이유, 버린 대안
4. **변경 범위**: 건드릴 파일과 영향받는 곳
5. **구현 단계**: 순서가 있는 작은 단계. 각 단계가 끝났는지 확인하는 방법 포함
6. **검증 방법**: 어떤 테스트나 확인으로 완료를 판단하는가
7. **열린 질문**: 아직 정해지지 않은 것

저장 위치는 프로젝트 지침에 규칙이 있으면 따르고, 없으면 사용자에게 묻는다. 정하지 못하면 레포 루트에 `<주제>-spec.md`로 둔다.

## 4. 확인받고 끝낸다

스펙을 요약해서 보여 주고 사용자의 확인을 받는다. 고치라는 요청이 있으면 문서를 고쳐서 다시 확인받는다. 구현은 사용자가 시작하라고 한 뒤에 한다.
